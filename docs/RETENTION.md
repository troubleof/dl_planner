# 版本与数据留存

此约定依据用户 2026-11-01 的新要求，替代此前每轮全量源码/实验打包的做法。

1. 一个长期维护的源码仓库，采用提交、分支和阶段标签记录版本。不要为每轮实验复制完整工程；不要提交 `source.tar.gz`、`evidence.tar.gz`、build/install、虚拟环境和缓存。
2. 长期保留中文报告、紧凑指标及失败清单、源码/配置、采用的模型权重、必要训练数组与协议。
3. 完整原始案例维持五个有明确目的的代表例，包含成功与失败。新增代表例时更新 `examples/cases/manifest.json`，重新评估旧例的保留价值；不要把整个 runs 目录提交进来。
4. 数据采集和标注期间可在被忽略的 `runs/` 中临时保留原始日志。先完成必要标签/诊断，再清理自己的临时产物；不得根据这条说明擅自删除其他工程或用户未指定的数据。
5. 候选自身分支数据可相关，地图划分必须独立，真值只用于离线标签/奖励，不得进入部署观测。缺失历史数据要如实标记，不能用历史归档校验说明声称完整数据仍在。
6. 修改权重、数据或五个案例后运行 `python tools/update_artifact_manifest.py`、`python tools/check_core.py`，并记录相应源码提交。更新清单只是建立新版本的哈希索引，不等于新模型通过了性能或安全验证。
7. 单个保留资产达到 50 MiB 时先考虑去重、分片或有明确用途的外部资产存储，避免仓库反复积累大二进制；现有资产均低于此线，无需 Git LFS 下载才能使用。

常用流程：

```bash
git switch -c codex/<简短主题>
# 修改、检查，必要时运行小规模仿真。
git add src tools config README.md docs
# 有真实模型/数据更新时，再显式加入相应权重、数据和哈希清单。
git diff --cached --stat
git commit -m "描述具体改动与行为"
git push -u origin HEAD
```

主分支合入采用普通提交/快进或 PR，不强制覆盖远程历史。继续保留失败结果，不能通过放宽地图/过期/接续检查或瞬时冻结来提高成绩。
