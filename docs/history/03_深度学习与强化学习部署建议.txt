后续深度学习与强化学习部署建议
本文件给出设计与部署建议，本轮没有训练神经网络，也没有验证模型的真机性能。
具体瓶颈的定量依据见 01_感知瓶颈实验结果.txt；不要把建议中的预期收益当作实测结果。

先把学习模块放在哪一层

优先考虑轻量的规划调度或候选选择：根据当前地图、路径状态和时间预算，选择复用、局部修复、完整搜索，后续再加入有限的速度档位。
这样能保留现有 EGO 优化器和提交验证，直接使用已经建立的计算、接续和失败日志。
固定的队列冲突和过期门限应先用可解释规则处理，再评估学习策略是否能在未见场景中进一步降低飞行时间和计算开销。
单纯用网络学会绕开确定性接口问题，不能证明学习方法优于修复接口。

如果希望使用点云深度学习，可以让小型点云或局部栅格编码器预测候选路径质量、可行概率或预计规划耗时，给搜索和优化排序。
预测的自由空间或点云补全不能直接写入“已确认自由”的安全地图；未观测区域的网络猜测应保留不确定性。
当前稀疏点数实验只改变理想水平采样，不能证明模型对真实缺失点、细杆漏检、反光材质、定位误差或扫描畸变的鲁棒性。

建议的第一版接口

观测：自机速度/加速度、机体系目标方向、局部占据/自由/未知表示、当前参考路径、最近更新的相关区域、最新帧年龄、上一轮耗时、剩余接续时间及近期拒绝原因。
当前实验已记录全局最新融合帧年龄；局部体素年龄和路径区域更新比例需要新增接口，不能把一个全局时间戳当作所有空间都刚被看见。
点云坐标最好统一到采集时机体系或明确的局部坐标系，固定尺度归一化，并保留有效回波/量程截断掩码。
现有仿真无回波端点位于 range+0.1，它们用于射线自由更新，不应被学习编码器误当作实际障碍表面。
丢帧和延迟条件下，同一帧被重复读取不代表新观测；输入中需要明确帧年龄或有效观测标记。
先试当前状态加短历史堆叠；只有证据表明历史不足，再考虑 GRU/LSTM。循环网络部署时需正确维护隐藏状态并在任务重置时清空。
动作：先用有限集合 {复用、局部修复、完整搜索}；要求选择无效时能进入确定的回退流程。
速度档位应在下一轮规划前选择，重新生成满足 P/V/A 连续性和动力学限制的轨迹；不能直接修改执行中曲线的时间尺度。
任何网络输出都经过当前的轨迹、地图、时序和接续检查；超时、非有限值或无可用输出时保留仍有效的原轨迹或已验证停车方案。
当前系统还没有全包络未知空间自由证明，保留检查不等于获得完整的真实飞行安全保证。

监督学习与强化学习的数据区别

已有 280 次日志适合定位失败原因、估计耗时、做输入时效诊断。
这些日志主要来自固定 repair 策略，不包含同一状态下其他动作的结果，不能直接作为“最佳决策标签”或完整离线 RL 数据集。
监督学习若要学习动作选择，需在相同起始状态、地图和预算下分别试算/回放候选动作，并用后续执行结果建立标签；不能把当次已执行动作自动标成最优。
强化学习需要可交互的环境包装，提供 reset/step、观测、动作、奖励、终止/截断语义；当前试验脚本还不是 Gymnasium 环境。
地图真值可以给训练时的专家、奖励或 critic 使用，但部署策略的观测不能读取真值障碍和未来点云。
Learning High-Speed Flight in the Wild 展示了在仿真中使用特权专家和模拟感知噪声进行训练的路线，并非必须人工标注真实目标位姿数据集：
https://arxiv.org/abs/2110.05113

训练与评价

若先做离散调度，可用小 MLP 的 PPO 作为可实现的基线；它不是已证明最佳算法。
先与固定 repair、固定 full、路径质量门限和预算门限等规则策略比较，确认学习收益不是来自放宽安全限制。
奖励同时包含目标进展、任务完成、飞行时间、实际规划成本、无效/超时决策；碰撞和不可执行状态要显式记录。
不能仅用距离目标的奖励，否则可能学会快速进入未知区域；也不能只奖励少算，否则可能学会停着不动。
碰撞惩罚不替代执行前验证。超时截断与碰撞终止需区分。
按地图实例/轨迹划分训练、验证、测试，不能把同一段轨迹的邻帧随机拆到训练和测试两边。
41/42/101/102 等地图已反复用于工程测试，今后学习的最终测试集应另建未见地图。
训练时随机化点数、帧率、固定/抖动延迟、独立/连续丢帧，并逐步加入位姿误差、测距噪声、细障碍、控制跟踪误差和制动能力变化。
本轮只测静态障碍和固定传输延迟；尚未给出动态障碍或延迟抖动条件的成绩。
训练计时可以用经过实测校准的成本模型提高吞吐，最终评价必须重新计入真实推理、规划和验证时间。
至少使用多个训练随机种子，冻结测试设置，分别报告完成率、碰撞/不安全前缀、飞行时间、路径长度、P95/P99、失效回退与最差案例。
SB3 官方建议使用独立评价环境、归一化观测并做多次运行：
https://stable-baselines3.readthedocs.io/en/master/guide/rl_tips.html
循环策略的隐藏状态与 episode_start 管理：
https://sb3-contrib.readthedocs.io/en/master/modules/ppo_recurrent.html

实际部署的时间预算

当前 300 ms 接续和 25 ms 提交保护意味着，候选从触发到提交的可用窗口小于 275 ms。
这个窗口还要容纳固定注入的 80 ms、地图更新、规划、最新地图复核、进程通信、发布和时钟量化。
不要把剩余名义时间全分给网络：高帧率下还存在新帧到达导致重复取消的问题，平均推理快并不代表提交能成功。
使用 batch=1 测量“观测形成→预处理→内存传输→推理→输出检查→规划/验证→提交”的完整链路，并单独记录冷启动、预热后 P50/P95/P99 和最大值。
小 MLP 先测 CPU；点云/CNN 编码器再比较 CPU 与目标 GPU。不能假定 GPU 在小批量下必然更快。
可以导出 ONNX 后通过 C++ 接入；逐样本核对归一化、坐标变换、掩码、动作缩放以及导出前后的数值一致性。
运行时保存模型版本、输入规格、归一化统计、推理耗时及对应地图版本。网络预测不得回填到已经过去的接续时刻。
ONNX Runtime 官方说明 CPU/GPU 数据复制会显著占用推理时间；应结合 I/O Binding 和 profiling 检查，而非只看网络算子耗时：
https://onnxruntime.ai/docs/performance/tune-performance/iobinding.html
https://onnxruntime.ai/docs/performance/tune-performance/profiling-tools.html

建议实施顺序

1. 用本轮结果选择需要先处理的确定性系统瓶颈，建立规则基线。
2. 给调度动作增加可交互接口，保留原优化器和验证器，跑通可复现的训练/评价环境。
3. 先试轻量监督学习或离散 RL 调度，评价是否优于规则策略。
4. 有明确收益后再增加点云编码器，并把其实际运行成本纳入闭环。
5. 在传感器回放和带控制动力学的仿真中验证，再进行受控真机验证。
这一路线不要求当前先采购更快传感器，也不要求先把整个规划器替换成端到端网络。
